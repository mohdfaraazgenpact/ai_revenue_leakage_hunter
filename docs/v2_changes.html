AI Revenue Leakage Hunter: v2 Changes

What changed between branch ai_revenue_leakage_hunter_v1 and ai_revenue_leakage_hunter_v2, and why. Synthetic data only.

Repo: mohdfaraazgenpact/ai_revenue_leakage_hunter Commits 63785e9, 0a4c280 15 Oct 2026 Plan v6 (integrity hardening)
Why v2 exists. An external source-code review of v1 found defects that could put wrong numbers in front of the jury: cross-currency comparisons, duplicates counted twice, an ignored compounding setting, and an evaluation that duplicate keys could distort. Its advice was to fix correctness and evaluation before adding features. v2 does only that. v1 stays on GitHub as the frozen baseline.

1. Priority fixes from the review (P0)

P0

Currency mismatch no longer creates false leakage

Change
If an invoice's currency differs from the contract's, the line goes to review (CURRENCY_MISMATCH) and is not priced.
Why
v1 compared a EUR invoice with a USD price and reported the gap as $50 of underbilling. There is no FX policy yet, so the engine must not convert or compare.
Where
src/reconcile.py · decision D-013 · open item B-007 (FX policy)
P0

Duplicate invoice lines are never counted twice

Change
An exact copy of a row is kept once. The copy gets status DUPLICATE and is left out of every total. Rows that share an ID but differ go to review, and so does the same invoice, SKU, date, quantity and amount under a new ID. Nothing is deleted.
Why
v1 processed every row independently, so a duplicated line doubled the leakage ($100 instead of $50). Adjustments keyed by line ID could also be applied twice.
Where
src/reconcile.py · D-014
P0

Simple vs compound escalation follows the contract

Change
The price calculation now reads the compounding setting. Simple escalation applies the sum of the rates to the original price. Both extractors read the convention from the contract wording, and the default stays compounding (D-004) when the contract is silent.
Why
The schema had the field, but the calculation ignored it. A 5% simple contract would have been priced at 110.25 instead of 110.00 after two years.
Where
src/price_schedule.py, src/extract/*, prompts/extract_terms.v2.md · D-010 · B-003
P0

Evaluation cannot be distorted by duplicate keys

Change
Evaluation checks that line IDs are unique on both sides before joining, and fails if they are not. It reports unmatched records, and the gate fails if there are any.
Why
A repeated ID could multiply rows in the join and inflate precision, recall and dollar totals.
Where
src/evaluate.py · D-018
P0

No silent fallback to the answer key

Change
A normal run without extracted terms now stops with a clear message. Using the answer-key terms requires --oracle. Those runs are labelled ORACLE in the outputs, and the app shows a warning banner.
Why
If extracted terms were missing, v1 quietly scored itself against the answers, which made a run look perfect.
Where
src/pipeline.py, src/reconcile.py, app · D-017

2. Data integrity

Rule: the engine never guesses and never drops a record silently. A line it cannot price safely goes to a review queue. It is never counted as a match or as leakage, and it is logged with its source file and row number in data/output/input_issues.csv.

ChangeWhyDecision
Each row is validated before any arithmetic: ISO dates only, numeric and non-negative quantity, price and amount, a 3-letter currency, and non-blank IDs.In v1, one bad date or blank amount crashed the whole run with a raw traceback, and valid rows produced no output.D-011
Ambiguous date formats such as 15/06/2024 are quarantined, not interpreted.15/06 and 06/15 can't be told apart, and a wrong date can change which price applies.D-011
Negative quantities and prices are rejected. Returns are booked as return_credit adjustments with a returned quantity.In v1, a −5 unit line was treated as an ordinary line, and its sign meaning was undefined.D-012
Only debit_note, credit_note and return_credit adjustments with positive amounts are accepted. Anything else sends the line to review.v1 treated any unrecognised adjustment type as a credit.D-012
Quantity × unit price must equal the line amount within $0.01, or the line goes to an invoice-integrity review.v1 took the root cause from the unit price but the dollar amount from the line amount, so the two could disagree inside one finding.D-015
An escalation clause whose date or rate couldn't be resolved sends the line to review.v1 priced such contracts as if the clause didn't exist. That was the main source of the rules baseline's $455k false overbilling.D-016

3. Evaluation and reporting

ChangeWhy
Underbilling, overbilling, review routing and contract-level metrics are reported separately.Overbilling is a different business problem and needs its own precision and recall.
Reports show true positives, false positives, false negatives and true negatives with their denominators, plus line-level dollar error and the number of correctly flagged lines with a wrong amount.An aggregate dollar error can hide line errors that cancel out. A correct flag with a wrong amount still matters.
Ground truth gains an expected_outcome column (MATCH / UNDERBILLING / OVERBILLING / REVIEW), and the gate checks that lines which must go to review actually do.Lines that need review must not count as ordinary matches.
The README results table is generated by the build and stamped with a dataset fingerprint, the generator seed and the git commit.Headline numbers must be reproducible and tied to the exact data and code that produced them.
Contract PDF and DOCX files are now byte-identical when regenerated from the same seed.Embedded timestamps made every rebuild look like a change in git.

5. App, prompt and documentation

ChangeWhy
"Unbilled revenue found" becomes "Potential underbilling (unvalidated)", "Estimated recoverable" becomes "Illustrative recoverable estimate" (with its basis shown), and the value calculator is marked "(simulated)".The labels presented candidates as facts (vetting UX-02).
CSV exports for findings, line results and input issues, plus a review queue in the Findings tab.Reviewers had no way to take results out of the app (UX-03) or to see lines that weren't reconciled.
Recoverability uses the latest invoice date in the run instead of a hard-coded date, and is labelled illustrative.The claim windows have not been validated by finance or legal (D-019, B-008).
Prompt v2 adds the compounding field and an instruction to treat the contract as untrusted data.Reads the escalation convention and reduces prompt-injection risk (AI-04).
Streamlit is set to run headless.tasks.ps1 app no longer stops at the first-run email prompt.
New: decisions D-010 to D-019, blockers B-007 to B-009, docs/release_gates.md, docs/jury_storyline.md, and plan v6.Every rule change is recorded for mentor sign-off, with a clear line between what is proven and what is not.
